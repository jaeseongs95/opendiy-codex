# R32: 공식 버전 갱신과 CLI·서버 전환 설계

상태: R32에 포함한 설계. 갱신 도구·전환 기능의 구현 및 실행 검증은 미완료다. R31 동결 소스 `1cd3bbff28286f081ee3bda32487c0313430ad2c`와 진행 중인 빌드를 변경하지 않는다.

## 목적과 확인한 문제

공식 새 버전이 나오면 공식에서 해결한 결함의 패치를 제거하고, 남은 수정만 이식해 검증된 CLI·서버 묶음으로 교체한다. 공식 실행 파일 하나를 덮어쓰면 OpenDIY 수정이 보존되는 구조는 아니다.

현재 공개 소스 `9b05bfdba74c648982def416ad48ffffc7b8a1b5`에서 확인한 경계는 다음과 같다.

- `SOURCE_BASELINE.json`과 `upstream/source-inventory.json`이 공식 원본·패치 소스·파일 해시를 식별한다. 그러나 `scripts/source-import/export.py`와 `verify.py`에도 버전·커밋·파일 개수가 중복 고정되어 있어 갱신 때 여러 곳을 수정해야 한다.
- 기존 내보내기는 파일 충돌·기존 변경·공개 제외 경로를 검사한다. 이를 버리고 새 소스 복사기를 만들지 않는다. 전체 차이 파일 중에는 변경 고지문만 붙은 파일도 있으므로 파일 개수를 패치 기능 수로 세지 않는다.
- `tools/windows-cli/package_cli.py`는 동결 소스와 공식 보조 파일의 기반 버전, CLI 버전·해시를 검사하고 새 폴더에 포장한다. 같은 기반의 별도 서버와 Desktop 조합까지 묶어 검증하는 책임은 보강해야 한다.
- `app-server-daemon/src/prepare_install.rs`에는 기존 패키지 검사·별도 releases 폴더·선택 경로·작업 잠금·명시적 `update --from-cli`가 있다. 이 명령은 실행 중 서버를 재시작할 수 있으며 진행·대기 작업이 없다는 것을 보장하지 않는다.
- 실제 경고에서 R30 CLI와 R28 공유 서버가 함께 실행되었다. 새 CLI를 선택해도 건강한 기존 서버를 재사용하는 동작이므로, CLI 파일 교체를 서버 전환 성공으로 보고하면 안 된다.

## 1. 공식 원본과 유지할 패치를 분리한다

기존 내보내기 도구에 작은 입력 명세를 추가한다. 계획한 입력 파일 `upstream/release-input.json`에는 공식 버전·태그와 고정 커밋, 이식 후보 커밋, 검토한 이전 공개 커밋, 배포 대상과 패치 목록 참조를 둔다. `SOURCE_BASELINE.json`은 계속 검증 결과이며 입력 명세와 역할을 섞지 않는다.

내보내기와 검사기는 동일한 입력을 읽는다. 공식 커밋과 후보의 실제 Git 객체, 검토한 패치 및 이전 공개 파일을 대조하고 기존 출처 목록을 생성·검사한다. 예상 파일 개수는 고정된 입력·출처 목록에서 얻는다. 현재 파일을 세어 그 숫자와 해시를 정답으로 다시 승인하는 방식은 금지한다. 임의 SHA를 받았다는 이유만으로 공식 태그와 일치한다고 간주하지 않는다.

패치는 기능·결함별로 구분하되 소스 구조를 플러그인 체계로 다시 만들지 않는다. 작은 패치 목록에 기존 소스 커밋 또는 검토한 차이 파일, 수정 이유, 실제 실패 경계의 회귀 시험을 연결한다. 새 버전마다 다음 판정을 남긴다.

| 판정 | 기준 | 처리 |
|---|---|---|
| 공식 해결 | 같은 실패 경계가 공식 코드에서 통과 | 해당 로컬 수정을 제거하고 시험은 보존 |
| 그대로 이식 | 공식에 결함이 남고 기존 수정이 같은 의미를 유지 | 기존 커밋·차이를 재사용 |
| 조정 이식 | 함수·모듈·규약이 달라져 기존 수정이 직접 적용되지 않음 | 달라진 경계만 수정하고 회귀 검증 |
| 판정 불가 | 재현·출처·호환성 근거 부족 | 미확정으로 두고 완성 후보에 자동 포함하지 않음 |

텍스트 충돌이 없거나 `git cherry-pick`이 성공한 사실만으로 이식을 승인하지 않는다. 공식에 동등 기능이 생겼으면 중복 구현을 유지하지 않는다. 누적 대형 패치를 매번 통째로 덮어쓰는 방식도 사용하지 않는다.

## 2. 기존 빌드 캐시와 포장 도구를 재사용한다

작업은 `D:/codex/build/<작업 식별자>/`의 별도 후보에서 진행한다. 공식 갱신 입력·유지할 패치·잠금 파일을 고정한 뒤 빌드하며, 빌드에 들어간 후보는 변경하지 않는다.

기존 target·의존성 캐시는 도구 체인, 대상, 기능 선택, 프로필과 컴파일 옵션을 대조해 재사용한다. 호환되는 캐시는 Cargo가 재사용하고 달라진 입력만 다시 컴파일하도록 한다. 새 버전이라는 이유로 전체 캐시를 삭제하지 않으며, 같은 target에 Cargo를 중복 실행하지 않는다. 도구 체인이나 잠금 파일이 달라지면 캐시 적중을 보장한다고 말하지 않는다.

검증된 CLI와 별도 app-server를 같은 후보 묶음으로 포장한다. 기존 공식 보조 파일의 기반 버전 검사도 유지한다. 묶음의 명세는 최소한 다음을 식별한다.

- 공식 버전·원본 커밋, 패치 후보 커밋과 동결 명세 해시
- CLI·별도 서버 각각의 버전, 상대 경로와 SHA-256
- 공식 보조 파일의 기반 버전과 파일 해시
- 실제 검증한 OpenDIY Desktop 실행 코드 커밋, 사용한 기능 선언과 시험 근거

생성한 묶음은 새 버전 폴더에 둔다. 기존 설치 파일을 덮어쓰지 않는다. 배포 전 패키지 자체의 두 실행 파일을 검사하고, 라이브러리 시험뿐 아니라 CLI 진입점의 컴파일도 확인한다.

## 3. CLI 선택과 실제 서버 전환을 구분한다

새 상시 업데이트 서버·데이터베이스·전역 설치 관리자는 만들지 않는다. 기존 패키지 releases/선택 경로, 잠금과 명시적 업데이트 명령을 사용한다. 시작 명령이 건강한 기존 서버를 보존하는 현재 동작도 유지한다.

사용자에게는 다음 세 값을 별도로 표시한다. 버전이 같아도 실행 파일이나 패치 후보가 다르면 같은 묶음으로 확정하지 않는다.

1. 선택한 CLI 패키지
2. 다음 서버 시작에 선택된 패키지
3. 실제 실행 중 서버의 버전·프로세스 시작 식별자·실행 파일 해시와 관측된 기능

설치 전에는 다음 상태로 구분한다. 준비 단계가 설치나 재시작을 수행해서는 안 된다.

| 상태 | 수행 및 판정 |
|---|---|
| 준비 | 새 묶음과 회귀·공동시험 결과를 검사하고 이전 선택을 보존 |
| 전환 대기 | 공유 서버에 연결된 담당과 신규 입력·예약 제출을 조율하고 진행·대기 작업을 확인 |
| 전환 실행 | 단일 담당이 기존 잠금 아래 정확한 새 패키지로 기존 업데이트 절차를 한 번 실행 |
| 실행 확인 | 새 실제 서버와 CLI의 버전·해시·기능, Desktop의 동일 백엔드 연결을 확인 |
| 완료 또는 복구 필요 | 실행 확인이 모두 맞아야 완료; 실패·결과 불명은 실제 단계와 함께 보존 |

전환 직전의 빈 작업 목록 하나는 그 직후 새 요청이 없다는 보장이 아니다. 진행·대기 작업과 새 입력을 안전하게 정리했다는 근거가 없으면 기존 서버를 유지하고 전환을 보류한다. 새 자동 작업 배제 규약이 필요하다면 기존 규약의 실제 지원을 확인한 뒤 별도 검토하며, 이 설계만으로 지원한다고 가정하지 않는다. 단순 버전 불일치는 강제 종료 사유가 아니다.

CLI 바로가기 변경과 여러 프로세스의 교체를 전역 원자적 작업이라고 부르지 않는다. 전환 중에는 실제 혼합 상태를 표시한다. 이전 실행 세대의 늦은 성공 기록으로 새 전환의 실패를 덮어쓰지 않는다. 명령 시간 초과는 결과 불명이므로 서버 식별과 선택 상태를 대조하기 전 업데이트를 반복하지 않는다.

## 4. 복구 경계를 명확히 한다

새 버전 시작이 실패하면 이전 패키지와 선택 정보를 이용한다. 기존 공식 선택·기동 경로를 재사용하며, 변경한 단계와 현재 실행 중 서버를 확인한 뒤 필요한 단계만 복구한다. 정상 실행 중인 이전 서버까지 다시 종료하거나 부분 실패를 성공으로 감추지 않는다.

실행 파일 복구와 사용자 데이터 복구는 별개다. 새 버전이 데이터 형식을 바꾸었다면 이전 실행 파일이 그 데이터를 읽을 수 있는지 확인해야 한다. 역호환성이 없거나 미확정이면 구버전을 운영 데이터에 연결하지 않는다. 기존 대화·인증·설정·데이터베이스를 임의로 덮어쓰거나 되돌리지 않는다. 격리 사본에서 호환성을 확인하고 승인된 복구 범위 안에서 처리한다.

이전 패키지는 새 실행과 공동시험·사후 확인이 끝날 때까지 보존한다. 다른 담당의 패키지, 유일한 검증 근거와 복구용 파일은 정리 대상에서 제외한다.

## 5. R32 수용 조건과 분업

| 경계 | 필요한 시험·근거 | 현재 상태 |
|---|---|---|
| 갱신 입력 | 버전·원본 커밋·이전 공개 커밋 불일치를 거부하고 기존 사용자 변경을 보존 | 미구현·미실행 |
| 패치 이식 | 공식 해결 패치 제거, 미해결 패치 재현·수정, 충돌 및 의미 변화 탐지 | 새 버전 대상 미실행 |
| 빌드·포장 | 동결 위반·잘못된 보조 파일·CLI/서버 혼합을 거부하고 두 진입점 검사 | 기존 일부 검사 재사용; 통합 미실행 |
| 공유 서버 보존 | CLI만 선택했을 때 기존 서버 미변경, 진행·대기·신규 작업이 불확실하면 전환 보류 | 통합 미실행 |
| 전환·실패 | 정확한 새 서버 확인, 기동 실패·명령 결과 불명·지연된 이전 성공의 오판 방지 | 미실행 |
| 복구·데이터 | 이전 패키지 복구와 데이터 역호환성을 별도 검사하고 사용자 데이터 불변 확인 | 미실행 |
| 두 프로젝트 | 같은 최종 묶음으로 Desktop 연결·도우미·모바일 원격의 실제 백엔드 확인 | 미실행 |

OpenDIY Codex 담당은 공식 원본·패치 판정, 빌드·포장 명세, 서버 업데이트·복구 절차를 맡는다. 서버를 교체하는 담당도 이 한 곳으로 둔다. OpenDIY Desktop 담당은 패키지 선택·실제 서버 상태의 구분 표시, 기존 도우미와 환경 전달, 전환 전 작업 보존 조율과 최종 공동시험을 맡는다. 양쪽에서 서버 업데이트를 중복 실행하지 않는다.

이 설계와 기존 캐시 설계를 R32의 같은 후보 관리에 연결하되 R31 빌드를 재시작하지 않는다. 실제 구현·회귀·새 독립감사·공동시험 뒤에만 릴리스와 설치 완료를 보고한다.
