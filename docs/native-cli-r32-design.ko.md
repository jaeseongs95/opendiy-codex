# R32 설계 교정안: 캐시 급락을 설명하고 확인된 결함만 고친다

상태: 설계 교정안. 현재 구현 후보 `2f42356a343c663ed2c03efede9a842b84d57dab`에 아래 사항이 모두 구현되거나 검증된 것은 아니다. 기반은 공식 0.166.0에 기존 결함 수정을 이식한 R31 `1cd3bbff28286f081ee3bda32487c0313430ad2c`다. 기존 동결본·설치·설정·빌드 캐시는 보존한다.

## 목적과 현재 판정

공식 기능을 재사용해 실제 캐시 적중률 급락의 원인을 구분하고, 확인된 로컬 결함만 수정한 실행본을 전달한다. 진단 파일이 생기거나 빌드가 성공한 것을 캐시 개선 완료로 보지 않는다.

현재까지 캐시 키·보존 시간·프롬프트 순서를 바꿔야 한다는 로컬 원인은 입증되지 않았다. 반면 다음 관측·호환성 문제는 소스 또는 격리 실행으로 확인했다.

| 구분 | 근거와 영향 | 최소 교정 |
|---|---|---|
| 캐시 응답 수집 누락 | 기존 생산자는 `codex_api::prompt_cache`의 DEBUG 이벤트를 내지만 기존 배치 수집은 INFO까지만 받는다. R32 초안은 이 부분을 수정한다. | 기존 파서·생산자를 그대로 사용하고 정확한 이벤트만 선택 수집한다. |
| 송신 조건과 응답의 연결 누락 | 기존 `WireObservation`의 `codex_api::prompt_cache_wire`는 R32 초안에서도 제외된다. 응답 숫자만으로 모델·키·도구·전송 조건 변화와의 관계를 판정할 수 없다. | 기존 요청 순번·응답 식별자·종료 상태와 허용된 지문을 같은 배치 경로에 연결한다. 별도 송신 계층을 만들지 않는다. |
| 구버전 설정 호환성 | 실제 R30에서 기존 설정은 종료 코드 0, 같은 파일에 `prompt_cache = true`를 추가하면 알 수 없는 필드 오류로 종료 코드 1이다. | 공용 `cli-logging.toml`에는 구버전이 아는 키만 유지한다. 새 기능은 전용 확장 파일로 읽는다. 구버전 파서를 느슨하게 바꾸거나 사용자 설정을 덮어쓰지 않는다. |
| 실행 세대 식별 공백 | 현재 배치에는 프로세스 번호가 있지만 파일의 UUID는 매번 새로 생성된다. 송신 순번과 비밀 없는 지문은 프로세스가 다시 시작되면 비교 범위가 달라진다. | 로그 시작 때 실행 식별자 하나를 만들고 모든 배치에 넣는다. 다른 실행 세대의 지문을 같은 값으로 비교하지 않는다. |
| 시험 경계 공백 | 초안의 배치 시험은 손으로 만든 tracing 이벤트를 주로 사용한다. 실제 생산자·응답 파서부터 파일까지 연결한 증거가 없다. | 기존 HTTP·WS 합성 전송 시험과 실제 파서를 배치 수집기에 연결해 검사한다. 실제 CLI 진입점도 배포 빌드 전에 시험 대상으로 포함한다. |

## 보존하는 구조

공식 요청 생성·HTTP/WS 전송·응답 파서·원본 사용량 전달·기존 토큰 계산을 재사용한다. 기존 비동기 큐, 로컬 버퍼, 날짜 폴더와 완결 파일 게시도 유지한다. 새 서버, 상시 감시기, 데이터베이스, 원문 요청 저장소, 대화 형식 또는 원격 호출을 추가하지 않는다.

송신 지문은 전송 조건의 차이를 찾는 보조 근거다. WS의 delta 입력을 논리 대화 전체로 부르지 않고, 임의 metadata 변화나 재연결을 곧바로 캐시 실패 원인으로 해석하지 않는다. 해시 충돌 가능성 때문에 지문만으로 내용 동일성이나 인과를 확정하지 않는다.

## 수집과 설정의 최소 변경

- 기존 `cli-logging.toml`이 전체 기록·저장 위치·버퍼를 제어한다. 전체 기록을 끄면 확장 설정도 파일 기록을 시작하지 못한다.
- 계획한 확장 파일은 같은 `CODEX_HOME`의 `cli-cache-diagnostics.toml`이다. `response`와 `wire` 참/거짓만 두고, 파일이 없으면 둘 다 거짓이다. 기존 저장 위치·주기·인증·프로젝트 설정을 복제하지 않는다. 아직 지원되는 설정으로 안내하지 않는다.
- 응답과 송신의 정확한 두 DEBUG 대상만 허용한다. 일반 DEBUG/TRACE, 자유 문자열, 프롬프트·도구 결과·인증 정보는 제외한다. 양의 정수·0·누락·잘못된 형식은 구분한다.
- 기존 송신 관측의 `APP_CACHE_WIRE_DIAGNOSTICS` 명시적 선택을 재사용한다. 초기화 때 확장 설정과 환경 선택을 한 번 해석해 불변인 실제 관측 모드를 만들고 기존 관측·수집 경계에 전달한다. 생산자와 필터가 환경을 각자 다시 읽지 않게 한다. 배치 송신 보존은 응답 수집·`wire` 선택·생산자 선택이 함께 충족될 때만 활성화한다. 기존의 명시적 환경 선택으로 다른 로그 경로에서 송신 진단을 쓰던 동작도 보존한다.
- 실행 중 전역 환경을 바꾸지 않는다. 적용 시 해당 실행기의 환경에만 전달하며, 별도 서버·Desktop 실행 경로에서도 같은 초기화 값과 실제 활성 조건을 확인한다. 요청한 관측과 실제 활성 관측 및 비활성 사유를 별도로 기록한다. 실행 중 토글이나 새 설정 서비스는 만들지 않는다.
- 건강한 기존 공유 서버를 재사용하면 새 CLI·proxy·Desktop 자식의 환경값은 기존 생산자에게 전달되지 않는다. 기존 시작 기록·프로세스 식별 근거로 실제 생산 서버의 버전·실행 세대·실효 모드를 확인한다. 기존 실행·구버전·증거 부재는 비활성 또는 미확인으로 표시한다. 추가 초기화·재개·강제 서버 재시작으로 이 증거를 대신하지 않는다.
- `wire = false`는 배치 보존을 끈다는 뜻이다. 사용자가 별도로 지정한 기존 `APP_CACHE_WIRE_DIAGNOSTICS=1`까지 꺼졌다는 뜻은 아니다. 생산자 계산 0회 판정은 생산자의 실제 선택이 꺼진 경계에서만 한다. 해당 프로세스에만 적용할 환경값이 다른 동시 실행으로 새지 않는지도 검사한다.
- 시작 시 선택된 관측 모드와 실행 식별자를 작은 구조화 기록으로 남긴다. 설정 저장만으로 활성화를 주장하지 않는다. 무거운 지문 계산이 꺼진 경로에서는 기존 생산자의 계산 0회 보장을 유지한다.
- 정상 부하는 기존 60초 버퍼·5초 자원 표본·16MiB 배치 버퍼 상한을 사용한다. 파일에는 크기가 제한된 요약도 붙으므로 버퍼 상한을 파일의 정확한 바이트 상한으로 표현하지 않는다. 완성한 파일은 다시 수정하지 않는다. Drive 접근은 별도 작성 경로에 두고 모델 요청·화면 처리가 기다리지 않게 한다. 로컬 완성·G: 게시·클라우드 업로드는 별개다.
- 계측 포화·기록 실패·급종료로 빠진 표본은 손실로 표시한다. 손실 구간을 정상 수집이나 적중률 0으로 표시하지 않는다. 디스크 상한이 전체 프로세스 메모리 상한이라고 주장하지 않는다.

## 기록 이후 반드시 할 일

분석 단위는 실행 세대·프로세스·요청 순번·응답 식별자다. 기존 순번이 내부 재시도를 포함한 논리 요청인지 실제 전송 한 회인지 코드 경계에서 구분한다. 재시도·WS 연결 세대는 기존 필드가 그 의미를 충족할 때 재사용하고 없으면 미확정으로 남긴다. 가장 가까운 시간의 요청에 강제로 붙이거나 송신 순번 하나를 물리 요청 횟수라고 부르지 않는다. 중복 완료·순서 역전·식별자 없음·늦은 이전 연결 이벤트는 오결합·중복 집계 반례로 검사한다.

기존 수집기와 오프라인 분석을 사용하며 조회를 위해 추가 `initialize`·`thread/resume`를 호출하지 않는다. 다른 세션의 원문·개인 로그·운영 데이터베이스를 읽는 권한으로 확대하지 않는다. Drive의 자동 동기화는 기존 프로그램에 맡긴다. 진단 보강을 이유로 매 파일의 클라우드 상태 조회나 원격 파일 재읽기를 추가하지 않는다.

1. 같은 대상의 연속 요청에서 요청 조건, 완료·실패·취소, 반환 모델·등급, 유효한 사용량과 수집 손실을 연결한다.
2. 토큰 기준 적중률은 같은 유효 표본 집합의 `sum(cached_tokens) / sum(input_tokens)`로 계산한다. 요청 수 기준 비율과 구분하고 분모 0·누락·비정상 숫자는 미확정으로 남긴다. 전체 요청 수·유효 응답 수·실패·제외 사유를 함께 제시하며, 누락된 입력 토큰 수를 모르면 전체 토큰 기준 수집률은 계산하지 않는다. 기록이 완전하지 않은 구간은 완전한 구간과 섞지 않는다.
3. 압축·모델 또는 등급 변경·도구 변경·full/delta 전환·실행 세대 변경과 적중률 변화를 대조한다. 함께 일어났다는 사실과 원인을 구분한다.
4. 클라이언트가 잘못 바꾸거나 누락한 경계가 재현되면 그 지점만 수정한다. 같은 입력과 조건에서 수정 전 실패·수정 후 성공을 확인한다. 새로운 정책 변경이 필요하면 근거와 영향 범위를 별도 검토한다.
5. 로컬 원인이 특정되지 않으면 확인한 범위와 남은 판별 조건을 보고한다. 추정 정책을 구현하거나 캐시 적중률·비용 개선을 발표하지 않는다. 관측 결함 수리와 급락 원인 조사를 서로의 완료로 대체하지 않는다.

공식 [캐시 비교 진단](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics)은 `comparison_response_id`로 비교를 요청하며, 이는 이전 대화 로드나 캐시 동작 변경과 다르다. 공식 [캐시 문서](https://developers.openai.com/api/docs/guides/prompt-caching)는 모델 세대별로 키의 역할을 구분한다. 이 문서만으로 ChatGPT 로그인 백엔드의 옵션 지원을 추정하지 않는다. 따라서 비교 옵션 자동 전송, 보존 시간 강제 변경, 키 공유, 프롬프트 재배열·축약은 이번 확인된 교정에 포함하지 않는다.

| 실제 급락의 원인·효과 | 허용된 실제 기록으로 원인을 분류하고 특정한 로컬 결함에 한해 같은 조건의 수정 효과를 검증 | 미완료. 적중률 개선 주장 불가 |

## 순서와 두 프로젝트의 조합

R32에는 [공식 버전 갱신과 CLI·서버 전환 설계](native-cli-r32-upgrade-design.ko.md)도 포함한다. 공식 원본·패치 판정·포장 입력의 중복 고정을 줄이고, 기존 업데이트 경로를 재사용해 선택한 CLI와 실제 공유 서버를 함께 검증한다. 현재 R28 서버/R30 CLI 불일치처럼 실행 파일 교체만으로 서버까지 바뀌었다고 보고하는 일을 방지한다. 새 설계의 구현·전환·복구 검증은 아직 완료되지 않았다.

현재 R31 동결 빌드에는 손대지 않는다. R32는 위 설계에 맞춘 작은 변경과 실제 경계 시험을 먼저 끝내고, 후보를 고정한 뒤 기존 빌드 캐시로 빌드한다. 라이브러리 시험만으로 CLI 진입점이 컴파일됐다고 취급하지 않는다. 같은 target에 Cargo를 중복 실행하지 않는다.

OpenDIY Codex는 CLI·서버·계측·공통 규약을, OpenDIY Desktop은 화면과 실행·연결의 사용자 흐름을 맡는다. Desktop의 현재 실행 코드 후보는 담당자가 보고한 `2fefa895`이며 문서 후보 `2902dcfe`와 구분한다. 실제 공동시험 전에는 검증된 호환 조합이라고 부르지 않는다.

최종 인계에는 CLI·서버 각각의 소스·버전·실행 파일 SHA-256, Desktop 실행 코드 커밋, 활성 관측 설정, 같은 백엔드 식별 근거와 시험 결과를 한 묶음으로 고정한다. 양쪽 README에 같은 조합을 기록하고 최종 변경·근거로 독립감사를 받는다. 로그 생성·빌드·감사 중 하나만 끝난 상태를 전체 문제 해결로 보고하지 않는다.

이 문서는 설계 산출물이다. 새 구현·운영 설정·설치·릴리스 완료를 뜻하지 않는다.
